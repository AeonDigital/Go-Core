# xbridge

`xbridge` is the architectural foundation layer of the `Go-Core` ecosystem. It is designed to eliminate rigid global state and raw standard library dependencies from production code by providing decoupled interfaces, zero-overhead production wrappers, and factory utilities.

The core philosophy of this package is **"Test-Driven Distribution"**: every module ships with its own boundaries and pre-generated mock suites, giving consumers out-of-the-box cross-platform isolation and the ability to achieve 100% test coverage in their own applications.

---

## Directory Structure & Organization

To prevent flat-file clutter and mimic the Go standard library taxonomy without package name collisions, code is segmented into specialized subpackages utilizing the **`b`** (Bridge) prefix:

### 1. Virtual Go Standard Library (`/go`)
- `xbridge/go/bio/` — Basic input/output data streaming mechanisms.
  - `xbridge/go/bio/bfs/` — Specific nested block for active filesystem objects (`IFileBridge`, `IFileInfoBridge`).
- `xbridge/go/bos/` — Operating system operations, environment variables, and process lifecycle.
- `xbridge/go/bfile/bfilepath/` — Cross-platform filesystem path analysis and secure directory confinement.
- `xbridge/go/bruntime/` — System telemetry, memory stats, and execution diagnostics.

### 2. Internal Core Domain Bridges (`/<domain>`)
Dedicated folders mapping internal modules or distinct service clusters within the repository, ensuring that large-scale domain logic remains segregated.
- `xbridge/xfs/` — Storage and package bridge utilities specific to the internal file storage context.
- `xbridge/xnet/` — Abstracted network, sockets, or HTTP infrastructure boundaries.

## Architectural Conventions (The Blueprint)

To maintain compile-time predictability and strict compliance with automatic code generators (such as `xmocks`), any new bridge or expansion must adhere to the following structural engineering rules:

### 1. Strict Naming Schema
- **Interfaces**: Must be public, suffixed with `Bridge`, and prefixed with a capital `I` (e.g., `IOSBridge`, `IFilepathBridge`, `IFileBridge`).
- **Concrete Wrappers**: Must be private/unexported to enforce pure boundary encapsulation. They use a lowercase `s` and are suffixed with `Bridge` (e.g., `sOSBridge`, `sFilepathBridge`, `sFileBridge`).
- **Global Ingress Gateways**: A single public global variable named after the entity exposes the active service layer (e.g., `var OSBridge IOSBridge = NewOS()`).

### 2. Public Instance Generators (Factories)
Since concrete wrapper structs are unexported, packages must expose type-safe public constructors to instantiate them:
- **Service Singletons**: Instantiated via simple `New<Domain>` functions (e.g., `NewOS() IOSBridge`, `NewFilepath() IFilepathBridge`, `NewRuntime() IRuntimeBridge`).
- **Volatile Resources**: Instantiated via explicit target functions mapping the underlying source descriptor (e.g., `NewFile(f *os.File) IFileBridge`, `NewFileInfo(info fs.FileInfo) IFileInfoBridge`).

### 3. Compile-Time Contract Guards
Every bridge file must feature an explicit compile-time implementation guard right underneath its private struct declaration to prevent regressions during future refactorings:
```go
// Ensure at compile time that the private struct implements the public interface.
var _ IOSBridge = sOSBridge{}
```

### 4. Singletons vs. Volatile Products
- **Service Singletons** (`OSBridge`, `RuntimeBridge`) are persistent infrastructure routers. They live as global interface pointers that are easily hot-swapped at unit test boundaries.
- **Volatile Products** (`IFileBridge`, `IFileInfoBridge`) are short-lived, dynamic entities. **They must never have global variable instances**. They are manufactured under demand by service layers and safely mocked via standard return-injection inside tests.

## How to Consume Bridges in Tests

By exposing public boundaries alongside pre-generated mocks subdirectories (e.g., `xbridge/go/bos/mocks`), consumers can hijack system behavior instantly:

```go
package business_test

import (
	"testing"
	"://github.com"
	"://github.com/mocks"
)

func TestBusinessLogicFlow(t *testing.T) {
	// 1. Create a type-safe mock instance generated by xmocks
	mockOS := mocks.NewMockOS()
	
	// 2. Configure a predictable return path without touching the real disk
	mockOS.SetReturn.OpenFile(nil, bos.ErrNotExist)

	// 3. Hot-swap the public global gateway pointer
	oldOS := bos.OSBridge
	bos.OSBridge = mockOS
	defer func() { bos.OSBridge = oldOS }() // Gracefully restore original state

	// 4. Execute your black-box code under test...
}
```

## Generating Mocks Locally

Whenever an interface signature changes inside the ecosystem, regenerate its respective mock suite pointing to its local `mocks/` folder destination:

```bash
# Regenerating the OS service layer mock into its new isolated directory
go run ./xmocks --file=xbridge/go/bos/os.go --interface=IOSBridge --alias=OS --output=xbridge/go/bos/mocks/

# Regenerating the nested File descriptor mock
go run ./xmocks --file=xbridge/go/bio/bfs/file.go --interface=IFileBridge --alias=File --output=xbridge/go/bio/bfs/mocks/
```
