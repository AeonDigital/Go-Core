# sterr
================================

## 1. PURPOSE & PRINCIPLE

`sterr` (Structured Error) provides a lightweight, immutable, and terminal-friendly failure tracking interface for Go modules.
The absolute driving principle is to balance deep technical telemetry for backend developers with clear, actionable troubleshooting instructions for human CLI end-users, bypassing the complexity of full-scale error state engines.

&nbsp;


________________________________________________________________________________

## 2. ARCHITECTURAL DESIGN

### 2.1 Immutability & Thread-Safety

Every single mutation method exposed by the `sterr` API does not modify the underlying structure instance pointer. 
Instead, it triggers a cascading copy mechanism returning a pristine, isolated node allocated on the heap. This completely eliminates data race conditions when cascading errors through asynchronous micro-routines, concurrent Go-routines, or recursive processing loops.


&nbsp;


### 2.2 Stack Trace Automation

The package automatically hooks into the underlying OS process thread stack to isolate the target failure origin location.
By analyzing the runtime program counters, it dynamically constructs a fully qualified `package::FunctionName` context stamp without relying on expensive runtime reflection mechanisms.

## 3. FLUENT API INTERFACE REFERENCE

The public interaction contract is exposed through the `CliError` interface residing under the `sterrinterfc` package.

```go
type CliError interface {
    error

    // Mutation & Building (Returns new instances)
    SetMessage(format string, args ...any) CliError
    SetDevMessage(format string, args ...any) CliError
    SetUserMessage(format string, args ...any) CliError
    AppendDevMessage(format string, args ...any) CliError
    AppendUserMessage(format string, args ...any) CliError
    AppendLNDevMessage(format string, args ...any) CliError
    AppendLNUserMessage(format string, args ...any) CliError
    ClearDevMessage() CliError
    ClearUserMessage() CliError
    WithDepth(additionalDepth int) CliError

    // Getters & Telemetry Readout
    GetFunction() string
    GetDevMessage() string
    GetUserMessage() string

    // Boolean State Evaluators
    HasDevMessage() bool
    HasUserMessage() bool
    HasErrors() bool
}
```

## 4. CODE EXAMPLES

### 4.1 Basic Instantiation & Telemetry

```go
package xclifn

import (
    "github.com/AeonDigital/Go-Core/sterr/pkg/sterr"
)

func ParseRawArgs(rawArgs []string) (map[string]string, error) {
    if len(rawArgs) == 0 {
        // Automatically captures "xclifn::ParseRawArgs" as the function context location
        return nil, sterr.New().
            SetDevMessage("terminal input slice payload is empty").
            SetUserMessage("No argument was passed. Please enter a valid flag.")
    }
    return nil, nil
}
```


&nbsp;


### 4.2 Reusing Builders Inside Iterative Loops

To accumulate logging data within structural loops, developers must re-assign the local tracker variable to capture the cascading immutable snapshots.

```go
func ValidateBatch(tokens []string) error {
    var batchErr error = sterr.New()

    for i, token := range tokens {
        if token == "" {
            batchErr = batchErr.(sterrinterfc.CliError).
                AppendLNDevMessage("empty string segment located at index %d", i).
                AppendLNUserMessage("The item at position %d cannot be blank.", i)
        }
    }

    if batchErr.(sterrinterfc.CliError).HasErrors() {
        return batchErr
    }
    return nil
}
```


&nbsp;


### 4.3 Handling the Native Error Catch Block

When executing the central terminal application router, intercept the generic error signature and perform interface type evaluation to safely output resolved guidance.

```go
func Execute() {
    err := xclifn.ProcessSomething()
    if err != nil {
        // Technical Debug Telemetry Output for System Logs
        // Output format: [FUNC: package::FunctionName][MSG: developer message payload]
        logger.Log(err.Error())

        // Actionable End-User Response Resolution
        if cliErr, ok := err.(sterrinterfc.CliError); ok && cliErr.HasUserMessage() {
            fmt.Fprintf(os.Stderr, "Erro: %s\n", cliErr.GetUserMessage())
        } else {
            fmt.Fprintf(os.Stderr, "Fatal Error: %v\n", err)
        }
    }
}
```

## 5. STRING OUTPUT SPECIFICATIONS

This section details the strict formatting templates generated by the engine for telemetry and terminal interaction.


&nbsp;


### 5.1 Native Error Output (Developer Logs)

When invoking the standard `Error()` method, `sterr` synthesizes a structured string combining the functional tracing metadata and the internal technical diagnostics.

* **Template:** `[FUNC: <package>::<FunctionName>][MSG: <DeveloperMessage>]`

&nbsp;

#### Concrete Output Example:
```text
[FUNC: xclifn::ParseRawArgs][MSG: syntax error: short flag '-longer' exceeds the maximum limit of 3 characters]
```


&nbsp;


### 5.2 User-Facing Message Output (Terminal Interface)

When extracting the human-friendly payload via `GetUserMessage()`, the engine yields the exact raw text string instructions designed to guide terminal users toward execution fixes, completely isolated from internal code architecture leakages.

* **Template:** `<UserMessage>`

&nbsp;

#### Concrete Output Example:
```text
The short flag '-longer' is invalid. Single-character flags using only one dash (-) must be at most 3 characters long (e.g., -out).
```
